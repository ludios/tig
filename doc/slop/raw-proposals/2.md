# Syntax-highlighting tig diffs with VS Code fidelity — feasibility & implementation plan

Verdict up front: **feasible, and less invasive than it sounds.** tig already contains ~80% of the
rendering machinery (per-segment colored line cells, an external-filter hook on the diff pipeline,
an ANSI-escape-to-cells parser, dynamic color-pair allocation). What's missing is (a) a *general*
SGR decoder — the existing one recognizes exactly two escape codes — and (b) a filter process that
tokenizes diff content with VS Code's actual grammar/theme engine and emits ANSI. Neither is
research; both are engineering. Estimated total: **~1–2 weeks** for a solid v1.

Repos referenced below: `tig` = uploaded tig master (2.6.1-dev, `tig/NEWS.adoc:4`),
`vscode` = uploaded microsoft/vscode main, `one-monokai` = uploaded azemoh/vscode-one-monokai.

---

## 1. How VS Code colorizes, precisely

VS Code's coloring is TextMate tokenization plus theme scope-matching:

- Grammars are TextMate `.tmLanguage.json` files shipped as built-in extensions — 51 grammar
  extension dirs in `vscode/extensions/*/syntaxes/` (python, javascript, typescript-basics, sql,
  rust, clojure, shellscript, …; **elixir is not bundled** — it comes from the marketplace).
- The engine is the `vscode-textmate` library (`^9.3.2`) with `vscode-oniguruma` 1.7.0 (Oniguruma
  regex compiled to WASM) — `vscode/package.json:161-163`, wired up in
  `src/vs/workbench/services/textMate/browser/textMateTokenizationFeatureImpl.ts:267,382`.
- Per line, `grammar.tokenizeLine2(line, state, 500)` produces tokens carrying encoded color
  metadata, with tokenization state threaded line-to-line
  (`.../tokenizationSupport/textMateTokenizationSupport.ts:54`). The 500 is a per-line time budget
  in ms.
- Scope → color resolution is a trie built from the theme's `tokenColors` rules:
  `parseTokenTheme` / `TokenTheme` / `ColorMap` in
  `src/vs/editor/common/languages/supports/tokenization.ts:48,133,156,193`.
- Your theme is small: One Monokai defines **55 tokenColors rules using only 13 distinct
  foreground colors** (`one-monokai/themes/OneMonokai-color-theme.json`; editor bg `#282c34`).
  This matters later for the ncurses color budget.

A second layer, LSP-driven *semantic* tokens, sits on top of TextMate colors in VS Code (e.g.
rust-analyzer recolors a lot of Rust). No terminal pipeline will replicate that without running
language servers. Fidelity ceiling of this plan = "VS Code with semantic highlighting off." For
One Monokai the TextMate layer is what carries the look.

Exact-fidelity conclusion: to color "just like vscode," run the *same* grammars against the *same*
theme JSON with the *same* engine lineage. That is exactly what **shiki** does (vscode-textmate +
oniguruma under the hood), and its `@shikijs/cli` package exposes `codeToANSI(code, lang, theme)`
producing terminal escape sequences (https://shiki.style/packages/cli). Shiki loads VS Code theme
JSON directly, so `OneMonokai-color-theme.json` is consumable as-is
(https://shiki.style/guide/load-theme), and its bundled grammar set covers python, bash/zsh
(shellscript), javascript, typescript, sql, rust, clojure, **elixir**, and nix
(https://shiki.style/languages). PL/pgSQL rides the generic `sql` grammar, same as in VS Code —
imperfect there, identically imperfect here.

## 2. What tig already has (verified in source)

**Per-segment colored lines.** `struct box { const char *text; size_t cells; struct box_cell
cell[1]; }` with `box_cell = { enum line_type type; size_t length; }`
(`tig/include/tig/view.h:28-37`). The draw loop walks cells and emits each with its own
attribute: `draw_textn(view, cell->type, text, length)` (`tig/src/draw.c:588-607`). Cell budget
is 8192 per line (`tig/src/diff.c:89`, overflow reported gracefully after crash fix #1389,
`NEWS.adoc`). So arbitrary per-token coloring within a line is *already the rendering model* —
used today by diff-stat coloring, word-diff, and diff-highlight.

**External filter hook on the diff stream.** `set diff-highlight = <path>` pipes the entire
`git show … --no-color` output through an arbitrary external program before tig parses it:
`diff_init_highlight` swaps `view->io` for the filter's pipe via `io_exec`
(`tig/src/diff.c:46-73`; option semantics in `doc/tigrc.5.adoc:289-295` — "when set to true then
diff-highlight is used, else the option value is used as the path"). The stage view shares this
path (`tig/src/stage.c:782,818`), so staged/unstaged diffs get highlighting for free. Input to
the filter is guaranteed colorless (`--no-color` hardcoded in `diff_argv`, `tig/src/diff.c:32`).

**An ANSI-to-cells parser — but a toy one.** Lines containing ESC are routed to
`diff_common_highlight` (`tig/src/diff.c:386-387`), which scans for exactly two sequences,
`\x1b[7m` / `\x1b[27m` (reverse video on/off), alternating cells between the base type and
`LINE_DIFF_{ADD,DEL}_HIGHLIGHT` (`tig/src/diff.c:288-302`). Crucially, the `skip` mechanism
strips the escape bytes from the stored text (`tig/src/diff.c:101-102,112-114`), so search,
regex, and text export operate on clean text. This is the exact skeleton the general SGR decoder
extends.

**Dynamic color machinery.** Line rules grow at runtime (`init_line_info` / `add_line_rule`,
`tig/src/line.c:103-121,150-180` — this is how tigrc's quoted-string custom color rules work),
and color pairs are deduplicated by (fg,bg) and allocated on demand via `init_pair`
(`init_line_info_color_pair`, `tig/src/line.c:197-218`). tigrc colors accept `color0..color255`
(`tig/src/options.c:383-394`; `doc/tigrc.5.adoc:1053-1056`).

**The one genuine gap: no truecolor.** tig speaks classic ncurses: 256 indexed colors, plain
`init_pair`, no `init_extended_pair`/direct-color. Truecolor has been an open request since 2014
(jonas/tig#227). Not a blocker: One Monokai's 13 foregrounds quantize to the xterm-256 cube with
barely visible error (`#e06c75`→204, `#98c379`→114, `#61afef`→75, `#c678dd`→176, `#e5c07b`→180,
`#56b6c2`→73, `#abb2bf`→249, `#d19a66`→173, `#676f7d`→243…). Pair pressure is trivial: ~13 fg ×
~4 bg contexts (default / add-tint / del-tint / cursor) ≈ 50 pairs, far under `COLOR_PAIRS`.
Exact 24-bit rendering can be a later, independent sub-project (ncurses ≥6 extended pairs +
`xterm-direct`, the approach discussed for kakoune in mawww/kakoune#1807).

## 3. Recommended architecture

```
git show --no-color ──► tig-syntax-filter (client) ──► tig
                              │  unix socket                │
                              ▼                             │ extended SGR decoder
                        highlight daemon                    ▼
                        (shiki: vscode-textmate       box cells per token
                         + oniguruma + One Monokai    → line types → ncurses pairs
                         theme JSON)
```

Two components, cleanly separable and independently testable:

**Component A — the filter (no C, exact VS Code colors).** A program that reads a unified diff on
stdin and writes the same diff on stdout with SGR sequences injected *inside* line bodies. Rules
it must obey, derived from tig's parser:

1. Preserve the diff structure byte-for-byte outside of injected SGR: `get_line_type` classifies
   lines by literal prefix (`diff --`, `@@`, `+`, `-`, … — `tig/include/tig/line.h:24-42`) on the
   raw line *before* escape stripping (`tig/src/diff.c:307`), so column 0 must stay clean. This is
   also why delta cannot be dropped in as-is: it reformats hunk headers and layout, which would
   break tig's classification. The filter is an SGR *injector*, not a reformatter.
2. Track the current file's language from `+++ b/<path>` extensions (plus shebang sniffing for
   extensionless scripts); reset grammar state at each file header.
3. Tokenize hunk body lines minus their first column, threading TextMate grammar state across
   consecutive lines of the same version (interleave: `-` lines continue the old-file state, `+`
   and context lines the new-file state — two parallel state chains per file).
4. Strip or escape any pre-existing ESC bytes in content (diffs *of* files containing escapes)
   before injecting its own, so tig's decoder can't be confused.
5. Flush per file (or per N lines) — tig streams the filter's stdout incrementally through its io
   layer, so a fully-buffering filter would stall the async view load.

Engine choice inside the daemon:

| Engine | Fidelity vs VS Code | Speed | Runtime | Notes |
|---|---|---|---|---|
| shiki (vscode-textmate + oniguruma) | exact (same engine + your theme JSON as-is) | good after warmup; WASM+grammar init tens of ms, then ~10³–10⁴ lines/s | Node/Bun | `codeToANSI` exists today; daemonize to amortize startup |
| syntect (Rust; what delta/bat use) | close, not exact (Sublime syntaxes; theme must be converted VS Code JSON→tmTheme, e.g. json2tm) | very fast | native single binary | good fallback if Node dependency is unacceptable |
| tree-sitter | different tokenization model; won't match | fastest, incremental | native | wrong tool for "just like vscode" |

Recommendation: **shiki daemon + thin client**. The daemon is ~200 LOC of TypeScript: load One
Monokai JSON + needed grammars once, listen on a unix socket, accept `(lang, state_id, line)` or
whole-hunk batches, return ANSI. The client is a dumb pipe (could even be a small C or shell
stub). Node cold-start (~60–150 ms) happens once per login session, not per diff view. If the
extra moving part offends, `bun build --compile` the whole filter into one binary and accept
~30–50 ms per diff open instead — still fine, since tig loads views asynchronously
(`begin_update`, `tig/src/diff.c:38`).

**Component B — the tig patch (C).** Generalize the existing decoder:

1. New option, e.g. `set diff-syntax-filter = <cmd>`, reusing the `diff_init_highlight` io-swap
   plumbing verbatim (`tig/src/diff.c:46-73`). Keep `diff-highlight` untouched; make the two
   mutually exclusive (as word-diff already excludes diff-highlight, `tig/src/diff.c:49`).
2. Replace the two-code scanner with a real SGR parser in `diff_common_highlight`'s slot
   (`tig/src/diff.c:288-302`): recognize `ESC[…m` with parameters 0 (reset), 1/3/4 (bold, italic,
   underline → `A_BOLD`/`A_ITALIC`/`A_UNDERLINE`), 38;5;N (256-color fg), 38;2;r;g;b (truecolor
   fg, quantized to xterm-256 for now), 39 (default fg). Ignore everything else. Keep the
   existing `skip` semantics so stored text stays escape-free.
3. Map each distinct resolved (fg, attr, bg-context) to a dynamically created line type via the
   existing `init_line_info`/`add_line_rule` growth path (`tig/src/line.c:103-121`), memoized in
   a small hash. Pairs then fall out of the existing dedup allocator
   (`tig/src/line.c:197-218`). Add a cap + fallback-to-default to guard pathological input
   (`COLOR_PAIRS` can be 256 on stingy terminfo).
4. Background composition: token colors carry fg only; bg comes from tig's own
   `diff-add`/`diff-del`/`default` line colors so added/removed lines keep their tint and the
   cursor row keeps working (cursor handling: `tig/src/draw.c:689`). Concretely, the decoder keys
   line types on (fg, attr) × current base line type's bg.
5. Colors are (re)initialized at startup and on `:set` from the prompt
   (`tig/src/prompt.c:1121`); the dynamic-rule path must be idempotent under that re-init.

Effort: decoder + type/pair management + option plumbing ≈ 400–700 LOC of C, 2–4 days including
tests (there's a ready-made harness pattern in `tig/test/diff/diff-highlight-test`). Filter +
daemon ≈ 300–500 LOC TS, 1–2 days for the hunk-level version.

## 4. The hard parts, honestly

**Mid-file tokenization state.** A hunk starts at line N of a file; TextMate state at line N
depends on lines 1..N-1 (block comments, template literals, heredocs). Options in ascending
fidelity/cost: (a) tokenize each hunk from initial state — right ~95% of the time, occasionally
wrong inside multi-line constructs; (b) **recommended v1.5**: the filter fetches full blobs
itself (`git cat-file blob REV:path`; it inherits the repo cwd since tig spawns it in
`view->dir`, `tig/src/diff.c:64`), tokenizes pre-image and post-image files once each, and maps
diff line numbers (from `@@ -l,c +l,c @@`) to per-line token runs — exact colors always, cost ≈
tokenizing two files per changed file, cacheable by blob SHA. Shiki's grammar-state API supports
(a); (b) needs only plain whole-file tokenization plus bookkeeping.

**Fidelity ceiling.** No semantic tokens (see §1) and no `editor.background` — tig keeps its own
background; One Monokai's fgs were designed against `#282c34`, so contrast survives on any dark
terminal background.

**Streaming.** Verified constraint, not a guess: tig incrementally reads the filter's stdout;
per-file flushing keeps first-paint latency at "one file's tokenization," tens of ms.

**Escape-in-content ambiguity.** Handled by rule 4 in §3 (filter sanitizes). Today's tig has the
same theoretical ambiguity with `7m`/`27m` and nobody notices; still, sanitize.

**Blame/blob/tree views** use the same box machinery but not the diff filter path — out of scope
for v1, natural v2 (this was literally requested in jonas/tig#229).

## 5. Phased plan

**Phase 0 — filter PoC, zero tig changes (½–1 day).** Write the shiki-based injector; validate
with `git show --no-color | tig-syntax-filter | less -R` in a truecolor terminal. Acceptance:
structure-preserving output (byte-identical after `sed 's/\x1b\[[0-9;]*m//g'`), colors visually
matching a VS Code window with One Monokai, elixir/rust/ts samples correct.

**Phase 1 — tig SGR decoder + option (2–4 days).** Patch per §3B. Acceptance: existing
diff-highlight tests still pass; new test fixture piping canned SGR diffs through
`diff_common_read` yields expected cell runs; search hits text with escapes stripped; `:set`
re-init doesn't leak or duplicate pairs; graceful fallback when the filter is missing (mirroring
the existing report at `tig/src/diff.c:534`).

**Phase 2 — daemonize + language coverage (1–2 days).** Unix-socket daemon, lazy grammar
loading, blob-SHA cache. Add the full-file-context mode from §4(b) behind a filter flag.

**Phase 3 — polish (optional).** Truecolor sub-project (ncurses extended pairs, closes the
quantization gap; independent value for tig upstream, ref jonas/tig#227). Blame view. Upstream
PR: split as (i) general SGR decoder — likely welcome, it generalizes an existing feature — and
(ii) docs/example filter.

## 6. Alternatives considered and rejected

**Drive a running VS Code instance.** No public extension API exposes TextMate tokenization of
arbitrary text with resolved colors (the tokenizer lives in the renderer/worker; extensions see
only semantic-token *providers*). You'd end up embedding vscode-textmate in an extension host —
i.e., running the same library with a VS Code-shaped anchor dragging behind it. Strictly worse
than the standalone daemon.

**Port vscode-textmate + oniguruma to C inside tig.** Months of work, links Oniguruma and a JSON
grammar loader into tig, duplicates a well-maintained ecosystem. Rejected on maintenance cost.

**delta as the filter.** Wrong on two axes: it reformats the diff (breaks tig's prefix-based
parser, §3 rule 1) and its syntect engine + tmTheme themes can't consume One Monokai JSON or VS
Code grammars, so colors drift. Its *architecture* (syntect, full-line background styling) is
still the right prior art for the Rust fallback path.

**tree-sitter.** Fast and lovely, but its scopes/token boundaries ≠ TextMate's, so "just like
vscode" is unachievable by construction.

## 7. Open questions before implementation

1. Is a Node (or Bun) runtime dependency acceptable on all four of your platforms? (NixOS/macOS
   trivially; Windows: tig runs under Cygwin/WSL — the daemon and socket path need a decision
   there, likely TCP-on-localhost or per-invocation mode.)
2. v1 scope: hunk-state tokenization (a) or full-file-context (b) from day one? (b) is the only
   way to be *always* right.
3. Quantized 256-color now with truecolor later, or gate the whole feature on the truecolor
   patch? Recommendation: quantize now; with One Monokai the delta is nearly invisible.
