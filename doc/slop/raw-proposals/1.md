> I would really like `tig` to syntax-highlight code in the diffs it renders. could you please come up with a good implementation plan to colorize code just like vscode does? (don't implement yet, just verify feasibility)
> 
> I don't really care how it gets done, whether it's porting code to do it, a bridge to some other library, interacting with a running vscode, etc; it should probably be reasonably fast, though.

## Verdict

**Yes—this is technically feasible with high confidence.** The best design is:

> **Have `tig` run a persistent local tokenizer sidecar built from the same `vscode-textmate` and `vscode-oniguruma` packages that VS Code uses, then render the resulting token spans through a new layered style system.**

That gives substantially better fidelity than approximating VS Code with Tree-sitter, `bat`, or a generic terminal highlighter. It also avoids depending on a running VS Code process or its unstable workbench internals.

For the supplied **One Monokai** theme, lexical highlighting can match VS Code at the token/theme level. Physical screen colors will be:

* exact RGB on terminals and terminfo entries exposing direct color;
* deterministically approximated on 256-color terminals;
* degraded gracefully on 8/16-color terminals.

VS Code’s syntax layer is based on TextMate grammars, with semantic tokens applied as a separate overlay. ([Visual Studio Code][1]) The supplied One Monokai theme does not enable or define semantic highlighting, so reproducing VS Code’s TextMate pipeline is the right fidelity target for this particular theme.

## What I verified in the uploaded sources

I inspected:

* `tig`, commit `1b86f070…`, reporting version 2.6.1
* VS Code snapshot `1.133.0`
* One Monokai `0.5.0`

I did not modify any files.

### `tig` already has most of the rendering primitive

`tig/include/tig/view.h` defines each rendered line as a `struct box` containing multiple `struct box_cell` spans. In `tig/src/draw.c:588-607`, the renderer iterates those cells and draws each span with its own line type.

That machinery is already used for things such as intraline diff highlighting. Consequently, syntax highlighting does **not** require replacing the curses renderer or turning every source line into one monolithic colored string.

The necessary change is to generalize a cell from:

> “this byte range has one `enum line_type`”

to:

> “this byte range has a lexical style plus zero or more UI overlays.”

### `tig` can identify which source line a diff row represents

The existing diff implementation already tracks:

* hunk coordinates;
* old and new line numbers;
* old and new paths;
* rename paths;
* parent/result sides;
* combined-diff state.

Relevant code includes:

* `tig/include/tig/diff.h`
* `tig/src/diff.c:625-654`, line-number mapping
* `tig/src/diff.c:727-775`, path mapping
* `tig/src/parse.c`, hunk-header parsing

This is enough to construct an explicit mapping from each displayed diff line to the corresponding old or new source document.

### The UI can accept results asynchronously

`tig/src/display.c`, `tig/src/view.c`, and `tig/src/io.c` already implement a nonblocking update loop around child-process pipes and dirty-line redraws.

So the intended experience can be:

1. Show the ordinary diff immediately.
2. Request highlighting for the visible file.
3. Continue accepting input and scrolling.
4. Attach syntax spans when the sidecar responds.
5. Redraw only affected lines.

The sidecar should have a service-level channel separate from the Git-output pipe owned by each view.

## The most important correctness constraint: tokenize complete files

It would be incorrect to tokenize each visible hunk independently.

A hunk may begin in the middle of:

* a multiline string;
* a block comment;
* a Markdown fenced block;
* an embedded `<script>` or `<style>` region;
* another grammar construct whose state began hundreds of lines earlier.

TextMate grammar state is carried from one line to the next. VS Code’s tokenizer exposes this through the previous rule stack; Shiki’s equivalent grammar-state support reflects the same requirement. ([Shiki][2])

Therefore each diff file needs two independently tokenized documents when both exist:

* **old document** for deleted lines;
* **new document** for added and context lines.

Mapping should be:

| Diff row    | Syntax source                    |
| ----------- | -------------------------------- |
| deletion    | old document                     |
| addition    | new document                     |
| context     | new document                     |
| diff prefix | diff UI style, not source syntax |

Only the currently relevant file needs to be tokenized initially. Large commits should not cause every changed file to be loaded and parsed upfront.

## Recommended architecture

```text
Git diff output
      |
      v
tig diff parser
      |
      +--> explicit diff_file model
      |       old/new paths and source identities
      |       hunk coordinates
      |       source-side mapping
      |
      +--> display-line references
              file id
              old/new line number
              diff-prefix length
              wrapped byte interval
                      |
                      v
           persistent tokenizer sidecar
           vscode-textmate + vscode-oniguruma
           VS Code language/grammar manifests
           One Monokai or another VS Code theme
                      |
                      v
           compact UTF-8 byte token runs
                      |
                      v
           layered style resolver in tig
              syntax
              diff add/delete/context
              intraline diff
              search
              cursor/selection
                      |
                      v
           curses direct-RGB / 256 / 16 backend
```

## Sidecar design

### Engine

Use these packages directly:

* `vscode-textmate`
* `vscode-oniguruma`

That is the same low-level grammar engine represented in the uploaded VS Code source. The snapshot uses:

* `vscode-textmate` `^9.3.2`
* `vscode-oniguruma` `1.7.0`

The helper would reproduce the relevant pieces of VS Code’s `TMGrammarFactory`:

* language ID to grammar scope mapping;
* grammar loading;
* injected grammars;
* embedded language mappings;
* token-type overrides;
* theme loading;
* Oniguruma WASM initialization.

The VS Code snapshot contains 83 contributed language definitions and 89 grammar contributions across its built-in extensions, so this gives broad default coverage without inventing a second language registry.

### Lifetime

Launch the helper lazily, once per `tig` process, and keep it alive.

A persistent process avoids repeatedly paying for:

* Node startup;
* Oniguruma WASM compilation;
* grammar JSON parsing;
* theme compilation.

A cross-session daemon would add stale-state, discovery, permissions, and protocol-version problems for relatively little benefit. A per-process helper plus an optional disk cache is simpler.

### Data returned

The helper should return resolved styles rather than raw TextMate scopes:

```text
style table:
    foreground RGBA
    optional background RGBA
    bold / italic / underline flags

per logical source line:
    start UTF-8 byte offset
    end UTF-8 byte offset
    style id
```

Returning resolved styles keeps the C side independent of TextMate selector semantics and dramatically reduces data volume.

Adjacent runs with the same style should be coalesced.

### UTF-16 versus UTF-8

This needs explicit handling.

JavaScript and `vscode-textmate` expose token boundaries in JavaScript string indices, meaning UTF-16 code units. `tig`’s cell lengths refer to bytes in UTF-8 text.

The helper must convert each token boundary to a UTF-8 byte offset before returning it. Otherwise non-ASCII text, emoji, and characters outside the BMP will misalign or split incorrectly.

### Protocol

For the final design I recommend a versioned framed binary protocol:

```text
magic
protocol version
message type
request id
payload length
payload
```

Benefits over unframed JSON include:

* arbitrary source bytes are representable safely;
* no need for a full JSON dependency in `tig`;
* less parsing and allocation;
* efficient compact line/run arrays;
* reliable recovery from partial reads.

A feasibility spike could use NDJSON to validate behavior quickly, provided it is treated as disposable and the source content is safely encoded.

The protocol should support:

* handshake and capability negotiation;
* theme registration;
* document tokenization;
* cancellation;
* cache invalidation;
* diagnostics;
* orderly shutdown.

Failure must be nonfatal: if the helper is absent, crashes, times out, or rejects a grammar, `tig` continues with ordinary diff rendering.

## Source reconstruction

The tokenizer needs the complete old and new documents, not merely the patch text. The implementation should introduce a `diff_file` model constructed during diff parsing rather than reconstructing everything later by rescanning display rows.

It should support these source cases:

| View             | Old document           | New document           |
| ---------------- | ---------------------- | ---------------------- |
| committed change | parent commit:path     | commit:path            |
| staged change    | `HEAD:path`            | index:path             |
| unstaged change  | index:path             | worktree path          |
| untracked file   | absent                 | worktree path          |
| rename/copy      | old path at old source | new path at new source |
| root commit      | absent                 | commit:path            |

Prefer immutable Git object IDs as cache identities. Asking Git for full index object IDs is better than relying on abbreviated IDs.

Textconv needs special treatment. If the diff displays transformed content, highlighting the raw blob could produce mismatched line and byte positions. Either:

* acquire exactly the same transformed source through Git’s textconv machinery; or
* disable syntax highlighting for that file and report the reason.

Binary files and submodules should be skipped.

Combined merge diffs should be deferred from the first implementation. There are multiple old-side documents and prefix columns, making the source mapping more involved. Highlighting only the result side could be an interim mode, but should not be presented as full parity.

Arbitrary patch input from stdin normally lacks the unseen source lines required to recover grammar state. It should default to plain rendering, with an explicitly named approximate hunk-local mode only if desired later.

## Wrapping requires new metadata

`tig/src/pager.c:72-105` currently splits a logical line into multiple display lines when `wrap-lines` is active. Those fragments do not retain their byte interval within the original source line.

The source reference attached to a display row therefore needs at least:

* source file ID;
* old and/or new logical line number;
* source-side designation;
* number of diff-prefix bytes;
* start byte within the logical source line;
* length of the displayed fragment.

Syntax runs can then be clipped to the wrapped interval without re-tokenizing or corrupting token boundaries.

This metadata should be built while parsing and wrapping, not inferred later from neighboring display lines.

## Renderer refactor

The current `enum line_type` is not rich enough to represent arbitrary theme colors and composable states. Dynamically generating hundreds of pseudo-line types would make configuration, redraw, and overlay behavior brittle.

A conceptual span should instead contain something equivalent to:

```text
byte length
syntax style id
intraline overlay id
```

The final style should be resolved at draw time from layers:

1. theme lexical style;
2. diff line state;
3. intraline word-diff state;
4. search match;
5. cursor or selected-row state.

This is necessary because current behavior is effectively destructive:

* selected rows suppress ordinary per-span styling;
* search uses `mvwchgat` to overwrite attributes and color pairs;
* word-diff highlighting assumes it owns the cell’s style.

Without compositing, adding syntax colors would cause cursor selection, search, and intraline diffs to intermittently erase one another.

### Recommended visual policy

Preserve the theme’s syntax foreground colors.

Represent diff state through:

* the `+`, `-`, or context prefix;
* a subtle line background tint;
* stronger background or attributes for intraline changes.

Avoid replacing all text on an added line with green and all text on a deleted line with red, because that destroys nearly all syntax information.

Retain a compatibility option for the existing full-line coloring behavior.

## Terminal-color implementation

The supplied One Monokai file has:

* 55 token rules;
* 13 explicitly used token foreground values;
* bold and italic styles;
* one foreground containing an alpha component;
* editor background `#282c34`;
* no semantic-token configuration.

Including VS Code’s default unscoped foreground gives only about 14 effective foreground colors. That is small enough that pair exhaustion is not a practical issue for this theme.

The backend should have four tiers:

1. **Direct RGB**
   Use extended curses color/pair APIs when the active terminfo entry genuinely exposes direct color.

2. **Reprogrammable palette, optional**
   When `can_change_color()` is available, allocate custom palette slots after saving their previous values. This should be opt-in because palette modification may affect the whole terminal session.

3. **Stable 256-color quantization**
   Map RGB to the nearest xterm-256 entry and cache the result. My calculation for One Monokai reduced its effective foreground set to 12 distinct xterm colors, which should remain recognizably close but is not exact.

4. **8/16-color fallback**
   Preserve contrast and semantic distinction as far as possible.

Ncurses provides extended color and pair APIs, but pair IDs beyond the legacy range also require the corresponding extended attribute-setting paths rather than simply applying the old `COLOR_PAIR` macro. Direct-color behavior remains dependent on the terminal and terminfo description. ([Invisible Island][3])

Alpha colors should be precomposited against the theme background before terminal conversion. Terminal foreground attributes do not perform VS Code-style alpha blending.

Italic should be emitted only when `A_ITALIC` and the terminal capability are available; otherwise omit it without changing token foregrounds.

## Why not the other approaches?

| Approach                         |                Fidelity to VS Code | Runtime properties                     | Assessment                      |
| -------------------------------- | ---------------------------------: | -------------------------------------- | ------------------------------- |
| Direct `vscode-textmate` sidecar |                            Highest | Fast after persistent warm-up          | **Recommended**                 |
| Shiki sidecar                    |                          Very high | Convenient API, some extra abstraction | Good spike or alternate backend |
| Running VS Code                  |                 Theoretically high | Heavy, brittle, lifecycle-dependent    | Reject                          |
| Tree-sitter                      | Moderate without extensive mapping | Very fast, native options available    | Future native fallback          |
| `syntect` / `bat`                |                        Approximate | Fast and mature                        | Useful fallback, not parity     |
| Port TextMate to C               |                   Potentially high | Large maintenance burden               | Reject                          |

### Shiki

Shiki is a credible alternative because it intentionally uses TextMate grammars and themes and the same class of Oniguruma-based engine as VS Code. It supports custom grammar definitions and preserving grammar state. ([Shiki][4])

It would make an excellent phase-zero prototype. Direct `vscode-textmate` is still preferable for the long-term helper because:

* `tig` only needs compact token runs, not rendered HTML or a syntax-highlighter presentation layer;
* it matches the VS Code source path more directly;
* there is less abstraction to adapt and version.

The helper protocol can make this choice replaceable.

### Running VS Code

The public VS Code extension and command-line surfaces do not provide a clean service for “return the raw TextMate token runs for this arbitrary document.”

Using workbench internals would entail:

* locating a compatible installation;
* starting or attaching to an editor/server process;
* loading private modules;
* reproducing extension-host and workspace state;
* coupling `tig` behavior to VS Code release internals.

It offers no tokenization advantage over using the underlying packages directly.

### Tree-sitter

Tree-sitter highlighting is driven by query captures whose names are mapped to presentation styles. Those captures are not equivalent to TextMate scope stacks. ([Tree-sitter][5])

Matching One Monokai would require:

* maintaining a capture-to-TextMate-style mapping;
* sourcing grammar-specific highlight queries;
* reproducing embedded-language and injection behavior;
* accepting differences in token boundaries.

It is attractive as an optional native backend, especially where Node packaging is undesirable, but not as the parity implementation.

### `syntect` or `bat`

This would be operationally simple and fast, but its normal syntax-loading ecosystem is Sublime syntax definitions rather than VS Code’s complete grammar contribution registry. ([Docs.rs][6])

It would produce good-looking output, not reliably “what VS Code shows.”

## Implementation plan

### Phase 0 — Standalone parity and performance spike

Do not touch `tig` yet.

Build a standalone helper that loads:

* the uploaded VS Code extension manifests and grammars;
* `vscode-textmate`;
* `vscode-oniguruma`;
* the uploaded One Monokai theme.

Use a golden corpus covering:

* C and C++;
* JavaScript and TypeScript;
* Rust;
* Python;
* Markdown;
* HTML with embedded CSS and JavaScript;
* multiline comments and strings;
* language injections;
* Unicode, combining characters, and emoji;
* very long or adversarial lines.

Compare token boundaries and resolved style IDs against VS Code’s token/scope inspector or a small harness using the equivalent VS Code registry configuration.

Measure:

* cold helper startup;
* first grammar load;
* warm tokenization;
* memory after several grammars;
* large-file behavior;
* pathological-line timeout behavior.

I was not able to obtain a trustworthy benchmark during this analysis because the available package registry did not provide `vscode-oniguruma`. I am therefore treating latency as a mandatory phase-zero gate rather than fabricating numbers.

Exit criteria:

* matching token boundaries and styles for the corpus;
* correct UTF-8 byte offsets;
* bounded behavior on pathological input;
* warm service latency that does not block interactive diff navigation.

### Phase 1 — Explicit diff/source model in `tig`

Add:

* one `diff_file` object per changed file;
* old/new path and source identity;
* hunk mappings;
* source retrieval strategy;
* a source reference on every logical/display line;
* wrapped-fragment byte intervals.

Test this model without rendering syntax colors.

Cover committed, staged, unstaged, untracked, renamed, and copied files before moving on.

### Phase 2 — Service protocol and helper lifecycle

Implement:

* lazy helper startup;
* handshake and protocol version;
* framed nonblocking I/O;
* request IDs;
* cancellation;
* helper health and restart policy;
* source and token cache;
* diagnostics that appear once rather than flooding the status line.

Make helper absence equivalent to the feature being unavailable, not a fatal initialization error.

### Phase 3 — Layered style model

Replace the assumption that every span has one fixed `line_type`.

Add:

* dynamic lexical style IDs;
* composable diff, intraline, search, and selection overlays;
* a draw-time style resolver;
* terminal pair caching;
* direct-RGB, 256-color, and limited-color backends;
* capability-dependent italic.

Preserve existing color configuration for users who do not enable syntax highlighting.

### Phase 4 — Asynchronous diff integration

Request tokenization in this order:

1. currently visible diff file;
2. adjacent file likely to be reached by scrolling;
3. other files only when idle or selected.

Render plain text until results arrive. When they do:

* reject stale responses by source identity and generation;
* attach run tables;
* mark only affected rows dirty;
* preserve scroll position and cursor state.

Cancel or deprioritize work when the user changes views rapidly.

### Phase 5 — Compatibility work

Integrate deliberately with:

* built-in word-diff spans;
* external `diff-highlight`;
* search results;
* selected-row rendering;
* horizontal scrolling;
* tabs;
* wrapped lines;
* custom themes and grammars;
* VS Code and VSCodium grammar discovery.

It may be reasonable for the first release to declare external `diff-highlight` and syntax highlighting mutually exclusive, then unify them after the style-layer work is stable.

### Phase 6 — Edge cases and hardening

Add or explicitly classify:

* textconv;
* combined merge diffs;
* stdin patches;
* malformed helper responses;
* grammar crashes or timeouts;
* cache bounds;
* source changes while tokenization is in flight;
* theme reload;
* helper version mismatch;
* fuzzing of the protocol and span clipping.

## Caching strategy

A cache key should include:

```text
source identity
language/grammar identity
grammar version or content hash
theme hash
tokenizer version
relevant tokenization options
```

Good source identities are:

* blob OID for historical revisions;
* index OID for staged content;
* path plus stat/content generation for worktree content.

Cache complete logical-line token runs, not display-line fragments. Wrapping and horizontal clipping can then be applied cheaply in `tig`.

Disk caching is optional. In-memory blob caching will already help when navigating between views or revisiting files in one process.

## Safety and resource limits

Mirror VS Code-like defensive limits rather than trusting every grammar and file indefinitely.

The uploaded VS Code code uses:

* a per-line tokenization time budget;
* a default maximum tokenization line length of 20,000 characters.

The helper should additionally impose configurable limits on:

* source file size;
* total token runs;
* runs per line;
* total tokenization time per document;
* number and memory size of cached documents.

On exceeding a limit, return a plain-text fallback for that file or line.

Grammar and theme search roots should be explicit trusted configuration. Paths must be passed without shell interpolation.

## Packaging

The major integration risk is packaging rather than tokenizer correctness.

For NixOS in particular, the helper should be wrapped with an explicit Node store dependency instead of assuming a mutable `/usr/bin/env node`. The same protocol allows distributions to package:

* `tig` core support;
* the Node helper;
* grammar assets;
* themes

as separate components.

A useful configuration shape would be approximately:

```text
set syntax-highlighting = auto
set syntax-highlighter-command = ...
set syntax-theme = ...
set syntax-grammar-path = ...
set syntax-color-mode = auto
```

`auto` should quietly fall back when the helper is unavailable.

The helper packages and One Monokai are MIT-licensed in the supplied snapshots, but bundled VS Code grammar assets should still receive a per-extension licensing and notice review before redistribution.

## Test plan

The existing `tig` screen-snapshot tests do not encode enough color/style information. Add a deterministic diagnostic form that dumps span metadata, for example:

```text
line 42:
    [0, 4) diff-prefix/delete
    [4, 7) syntax/keyword
    [7, 8) syntax/default
    [8, 15) syntax/function + intraline-change
```

Then test:

* multiline state beginning before the first displayed hunk;
* old versus new source state;
* renamed files;
* staged, unstaged, and untracked content;
* embedded grammars and injections;
* UTF-8 boundary conversion;
* a token split by wrapping;
* tabs and horizontal scroll;
* missing final newline;
* search over syntax spans;
* selected line over syntax spans;
* word-diff over syntax spans;
* direct-color and 256-color resolution;
* missing italic support;
* helper crash, timeout, and stale response;
* rapid navigation;
* worktree mutation and refresh.

## Risk assessment

| Area                          |                 Risk | Reason                                                                |
| ----------------------------- | -------------------: | --------------------------------------------------------------------- |
| TextMate tokenization         |                  Low | Mature upstream engine; VS Code-compatible grammar inputs             |
| Theme matching                |                  Low | One Monokai has a small conventional TextMate rule set                |
| Diff/source mapping           |               Medium | Several Git source modes and rename/textconv cases                    |
| Renderer/style composition    |          Medium–high | Current cursor/search/word-diff styling is destructive                |

## Recommended first-release scope

Include:

* ordinary two-sided commit diffs;
* staged and unstaged diffs;
* untracked files;
* rename/copy handling;
* built-in VS Code grammars;
* custom VS Code TextMate themes;
* asynchronous highlighting;
* direct-RGB and 256-color rendering;
* graceful plain-text fallback.

Defer:

* combined merge diffs;
* exact textconv unless transformed full sources are available;
* arbitrary stdin patches;
* semantic language-server tokens;
* bracket-pair colorization;
* attaching to a running VS Code instance.

## Bottom line

The implementation is worth pursuing.

The technically sound route is **not** to teach `tig` a new parser for every language and not to remote-control VS Code. It is to place VS Code’s TextMate tokenizer behind a small persistent protocol and make `tig`’s existing span renderer capable of dynamic, layered styles.

The tokenization portion is comparatively straightforward. The substantial work is:

1. preserving exact old/new source identity and byte mapping;
2. making wrapping retain source intervals;
3. replacing destructive line coloring with composable style layers;
4. providing robust terminal color fallbacks;
5. packaging the helper cleanly.

That design can reproduce One Monokai’s VS Code lexical highlighting accurately, remain responsive on large diffs through lazy asynchronous work, and preserve a clean fallback path when the helper or terminal capabilities are unavailable.
